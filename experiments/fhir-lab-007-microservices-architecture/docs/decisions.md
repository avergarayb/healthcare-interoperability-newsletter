# Decisions

## Two services

The patient read crosses an application boundary and a FHIR boundary. One Spring Boot process can hide both behind packages. Two processes make the network hop, the independent deployable unit, and the independent failure visible.

The parent `pom.xml` is only a Maven aggregator so `mvn test` runs both modules. It is not a shared parent and it does not publish a shared library.

## FHIR stays in the integration service

`fhir-integration-service` owns `fhir.base-url`, the `Accept: application/fhir+json` header, the `Patient` JSON subset, and the translation of FHIR errors.

`patient-service` calls `GET /internal/fhir/patients/{id}` and deserializes `id`, `firstName`, `lastName`, `gender`, and `birthDate`. The word `fhir` in that path names the integration route. The patient service has no FHIR resource model.

## No HAPI dependency in the patient service

`patient-service` depends on `spring-boot-starter-web` and `spring-boot-starter-test` only. A HAPI dependency there would let FHIR types leak into the application service even if the HTTP payload stayed small.

## No HAPI dependency in the integration service either

HAPI is useful when the code needs the full model or the validator. This lab reads five fields. Jackson records are smaller and still keep the FHIR parse on the integration side of the boundary. The external server remains the existing HAPI FHIR server on port 18080.

## Synchronous HTTP

The demonstration is a request that needs an answer before it returns to the client. `RestClient` matches that shape and matches the HTTP client already used for FHIR reads in earlier labs. WebClient was not added.

Kafka and other event-driven communication were left out on purpose. An event would not answer `GET /api/patients/{id}`. Asynchronous integration is a different boundary and is reserved for a later lab, not implemented here.

## No shared Java DTO library

`PatientResponse` and `IntegrationPatientResponse` are separate types in separate modules. Their JSON is structurally the same so the lab stays focused. Compile-time sharing would hide the fact that each service owns its contract and can evolve it without a shared artifact.

The patient service does not run a second field-renaming mapper. Adding one would only copy identical names.

## Errors are translated at each boundary

A downstream body can contain an `OperationOutcome`, a HAPI diagnostic, a stack trace, or a URL. Forwarding it would couple the caller to that implementation.

`FhirPatientClient` turns FHIR 404 into `PatientNotFoundException` and does not keep the response body. Other FHIR failures become `FhirClientException`. `ApiExceptionHandler` in the integration service emits a fixed `{error, message}`.

`FhirIntegrationClient` does not parse the integration error JSON. It maps status 404 to its own not-found exception and any other error status to `IntegrationUpstreamException`. Connection failure becomes `IntegrationUnavailableException`. The patient-service handler writes a new body.

## RestClient

Both outbound calls use Spring `RestClient`:

- patient service base URL: `integration.base-url`
- integration service base URL: `fhir.base-url`

The FHIR URL is not hardcoded in Java. Tests bind `MockRestServiceServer` to the builder and assert the resolved URL and, for FHIR, the `Accept` header.

## Unavailable integration service

When the patient service cannot open the connection, the response is **503** `integration_unavailable` with message `Integration service is not reachable`.

502 is reserved for the case where the integration service answers with an error or an unreadable body. That includes the case where the integration service is up and the FHIR server is not. Using one status for both hops would hide which boundary failed.

## Mapping assumptions

Lab-specific, not a general FHIR mapping:

- `firstName` is the first `given` of the first `HumanName`
- `lastName` is `family` of that same name
- `gender` and `birthDate` are copied as strings
- a missing name yields null name fields
- the logical id is taken from `Patient.id` and is not generated by this lab

HAPI logical ids in this environment come from an in-memory H2 database without a volume. An id observed in one container life is not a stable identifier.

## Timeouts

Both clients set a connect timeout of 2 seconds and a read timeout of 5 seconds through `SimpleClientHttpRequestFactory`. There is no retry. Either timeout is a `ResourceAccessException`. On the integration service that becomes 502 `upstream_unavailable`. On the patient service it becomes 503 `integration_unavailable`, because the integration call itself did not complete.

## Security

No authentication is implemented.

In a real environment, service-to-service communication and FHIR access would require authentication and authorization.

## Observability

No correlation id, trace exporter, metrics registry, or log aggregator is configured. Those are production concerns. This lab cannot reconstruct one request across both processes from telemetry it does not collect.

## Manual evidence

Recorded on 2026-10-16 against the local HAPI container `hin-fhir-lab-001` after `docker start`. The container had been exited, so this H2 lifecycle was empty. `GET /Patient/1000` first returned HTTP 404 `OperationOutcome` with `HAPI-2001: Resource Patient/1000 is not known`.

A temporary Patient was created with `POST http://localhost:18080/fhir/Patient` (UTF-8, no BOM):

- identifier `https://example.org/fhir/identifier/lab-007|LAB-007-PATIENT-001`
- name Lucia Example
- gender `female`
- birthDate `1988-03-20`

HAPI responded HTTP 201 and assigned logical id `1000` (`Location: http://localhost:18080/fhir/Patient/1000/_history/1`). That id belongs to this H2 lifecycle only.

With both Spring services running:

| Call | Result |
| --- | --- |
| `GET http://localhost:8089/api/patients/1000` | 200 `{"id":"1000","firstName":"Lucia","lastName":"Example","gender":"female","birthDate":"1988-03-20"}` |
| `GET http://localhost:8090/internal/fhir/patients/1000` | 200, same JSON fields. No `resourceType`. |
| `GET http://localhost:8089/api/patients/does-not-exist` | 404 `{"error":"not_found","message":"Patient does-not-exist was not found"}` |
| `GET http://localhost:8090/internal/fhir/patients/does-not-exist` | 404, same stable contract |
| `GET http://localhost:18080/fhir/Patient/does-not-exist` | 404 `application/fhir+json`, `resourceType` `OperationOutcome`, diagnostics `HAPI-2001: Resource Patient/does-not-exist is not known` |
| `GET http://localhost:8089/api/patients/%20` | 400 `{"error":"invalid_id","message":"Patient id must not be blank"}` |

The upper 404 bodies do not contain `OperationOutcome`, `HAPI-2001`, or the HAPI `X-Request-ID`.

After stopping the process on port 8090 and leaving port 8089 up:

`GET http://localhost:8089/api/patients/1000` returned 503 `{"error":"integration_unavailable","message":"Integration service is not reachable"}`. The body does not contain port 8090.

After starting the integration service again and stopping the HAPI container, with both Spring services still up:

| Call | Result |
| --- | --- |
| `GET http://localhost:8090/internal/fhir/patients/1000` | 502 `{"error":"upstream_unavailable","message":"FHIR server is not reachable"}` |
| `GET http://localhost:8089/api/patients/1000` | 502 `{"error":"upstream_error","message":"Patient data is temporarily unavailable"}` |

The patient-service body does not repeat the integration message, the FHIR base URL, or `HAPI-2001`. The HAPI container was started again after this check.

## Closure review

On 2026-10-16 the same checks were repeated after `mvn clean test` (14 + 17 = 31, 0 failures, 0 errors, 0 skipped). The H2 lifecycle was empty again: `GET /Patient/1000` returned `HAPI-2001` before any create.

`POST /fhir/Patient` for identifier `LAB-007-PATIENT-002` (Lucia Example, female, 1988-03-20) returned HTTP 201 and assigned logical id `1000` once more. The closure calls used that assigned id:

| Call | Result |
| --- | --- |
| `GET http://localhost:8089/api/patients/1000` | 200 application JSON, no `resourceType` |
| `GET http://localhost:8090/internal/fhir/patients/1000` | 200 integration JSON, no `resourceType` |
| `GET http://localhost:8089/api/patients/does-not-exist` | 404 `not_found` |
| integration process stopped | patient service 503 `integration_unavailable` |
| HAPI container stopped, both Spring services up | integration 502 `upstream_unavailable`; patient service 502 `upstream_error` |

None of those upper-layer bodies contained `OperationOutcome`, `HAPI-`, `ca.uhn`, `localhost:18080`, `:8090`, a Java exception class name, a stack trace, or `secret-internal-detail`. The HAPI container was started again and metadata returned HTTP 200.

## Later asynchronous integration

This lab stops at a synchronous request path. A later lab can introduce event-driven communication between services. That work should not be folded into this module: the failure and contract lessons here depend on a direct HTTP response.
